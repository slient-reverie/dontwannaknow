## 0. 本次故障的根因（先抓主要矛盾）

日志很长，但真正的根因只有两条：

```text
The requested module '@deepseek-ai/dsh-settings' does not provide an export named 'installSettingsSection'
@yuxianglin/dsh-bridge-browser: pending (waiting for service: apiProxy)
```

一条是 **ESM 具名导出缺失**（插件调用了核心没有的 API → 版本不兼容），

## 一、Node.js 与 npm

### 1.1 `npx` 是什么

- `npm` 是**包管理器**，负责安装包。
- `npx` 是**临时执行一个包**的工具：先看本地/全局有没有，没有就下到 npm 缓存里再执行。
- 我运行的 `npx.cmd @deepseek-ai/dsh web` 意思是：执行 `@deepseek-ai/dsh` 这个包的 `web` 命令。
- `.cmd` 是 Windows 上给命令行用的**批处理包装**（Windows 和 Unix 对可执行文件的处理方式不同）。

### 1.2 npm 缓存目录

```text
C:/Users/<你的用户名>/AppData/Local/npm-cache/_npx/1e7f6d9597241db0/node_modules/...
```

这就是 `npx` 下载的包存放位置。`_npx` 后面那串是**缓存 key**，不同版本可能对应不同目录（所以同一个包可能在缓存里有好几份）。

### 1.3 `package.json`

项目的「身份证」，核心字段：

| 字段 | 含义 |
|---|---|
| `dependencies` | 运行时依赖，比如 `dshmarket: ^1.36.0` |
| `dsh.profile.bundles` | dsh 自定义字段，告诉 dsh「**启动时要加载哪些插件包**」 |

> ⭐ **关键区别**：`dependencies` 只是「声明我装了它」，`bundles` 才是「启动时真的去加载它」。
> 我今晚删的是 `bundles`，不是 `dependencies`——所以**包还在，只是不加载了**。这就是「禁用插件」的正确姿势。

### 1.4 语义化版本（semver）

| 写法 | 允许升级的范围 | 例子 |
|---|---|---|
| `^1.36.0` | 同一个**大版本**内任意升级 | 可升到 `1.99.0`，**不能**到 `2.0.0` |
| `~1.36.0` | 只允许**小版本**内升级 | 只能升到 `1.36.x` |
| `1.36.0` | **锁死**这个版本 | 就是不升 |

> 这就是为什么 dsh 会「自动更新到不兼容版本」：`^` 允许它在 `1.x` 内一路升上去，而插件没跟上核心的 API 变化。

## 二、模块系统（ESM）

报错里最关键的一类：

```text
The requested module '@deepseek-ai/dsh-settings' does not provide an export named 'installSettingsSection'
```

这是 **ES Module（ESM）** 的导入错误：

- ESM 写法：`import { installSettingsSection } from '@deepseek-ai/dsh-settings'`
- 如果目标模块里**没有这个具名导出**，Node 直接抛 `SyntaxError`，**整个模块加载失败**
- 对比老的 CommonJS：

```js
const { installSettingsSection } = require('...')   // 加载时不报错，用到时才 undefined
```

> **结论：ESM 报错更早、更狠——一错就整个文件挂掉。** 排查时看到 `does not provide an export named`，本质是**版本不匹配**：插件按新 API 写的，装的核心是旧版（或反过来）。

## 三、插件架构与依赖注入（dsh 用的 cordis 框架）

### 3.1 插件树

启动时把所有插件按配置组装成**一棵树**，逐个加载。

> ⚠️ **任何一个插件加载失败，整棵树就失败**——这就是为什么两个小插件能把整个 dsh 拖崩。

### 3.2 服务（Service）与依赖等待

```text
@yuxianglin/dsh-bridge-browser: pending (waiting for service: apiProxy)
```

这是**依赖注入**的典型表现：

- 插件 A 声明「我需要 `apiProxy` 这个服务」
- 如果没有任何插件提供 `apiProxy`，A 就永远停在 `pending`，整棵树激活失败

> 同样的思想你在前端会再遇到：Vue 的 `provide/inject`、React 的 Context、后端 NestJS 的 DI——**依赖必须有人提供，否则消费方起不来**。

### 3.3 生命周期

| 状态 | 含义 |
|---|---|
| `pending` | 在等服务（还没激活） |
| `active` | 已成功激活 |
| `failed` | 加载失败 |

dsh 启动最后会检查「所有 entry 是否都 activate 了」，没激活就报 `1 entry did not activate`。

## 四、配置文件格式

### 4.1 YAML

- 靠**缩进**表达层级；**不能用 Tab，只能用空格**
- 同一个对象的字段必须**左对齐**

我今晚第一次用**记事本**改 YAML，缩进乱了，报错：

```text
bad indentation of a mapping entry (5:11)
```

正确写法：

```yaml
- id: dsh-market
  name: 'dshmarket'
  disabled: true
```

> 💡 **教训：改 YAML/代码用 VS Code，不要用记事本**——记事本不显示缩进、不改行尾、编码也可能踩坑。

### 4.2 JSON

- 严格格式：**不能有多余逗号**，字符串必须**双引号**
- **数组最后一个元素后面不能有逗号**
- 我今晚改 `package.json` 时，删元素要**同时处理逗号**，就是这个原因

### 4.3 三种文件的分工

| 文件 | 作用 |
|---|---|
| `package.json` | 声明依赖 + dsh 的 `bundles` 加载列表 |
| `cordis.yml` | profile 根入口，一般是空的 |
| `cordis.patch.yml` | 用户补丁层：覆盖 / 禁用 / 插入插件行 |

## 五、命令行与文件操作（PowerShell）

### 5.1 重命名 / 删除文件

```powershell
Rename-Item "路径" "新名字"
```

> ⭐ 我用 `.bak` 后缀「**软禁用**」插件，是很实用的技巧：**不删文件，只改名，随时能恢复。**

### 5.2 查看文件内容

```powershell
Get-Content "路径"
Get-Content "路径" -Raw      # 不换行，一次性输出
```

### 5.3 搜索文件内容（排查配置的黄金组合）

```powershell
Get-ChildItem "目录" -Recurse -File -Include *.yml,*.yaml |
  Select-String -Pattern '关键词' -SimpleMatch
```

**递归找文件 → 在文件里搜关键词**，这是定位配置问题的标准套路。

### 5.4 重复执行命令的「假报错」

第二次执行 `Rename-Item` 时报「不存在项」——**不是真 bug**，而是第一次已经成功、第二次找不到原名了。

> **看报错要结合上下文，别被重复操作的假警报带偏。**

## 六、调试方法论（今晚最值钱的部分）

今晚实际走了一遍标准排查流程：

1. **读报错，找第一个真正的错误**
   日志很长，但根因就两条：`does not provide an export` 和 `is not a function`。**别被后续的连锁报错淹没**。
2. **定位到具体文件**
   报错里直接给了路径：`.../profiles/web/node_modules/dshmarket/lib/settings.js`。
3. **判断是「不兼容」还是「配置错」**
   - 不兼容：插件调用了核心没有的 API → **禁用插件**
   - 配置错：YAML 缩进、JSON 逗号 → **改格式**
4. **二分法排查**
   一次禁用一批，重启看报错变没变；先禁两个，再禁第三个，逐步收敛。
5. **软禁用优于硬删除**
   改名 `.bak`，随时可回滚。
6. **改完必须重启验证**
   配置类改动不会热生效，必须重跑命令。

## 七、下次遇到同类问题：三步自查

1. **第一行真报错是什么？**（不是最后一行，不是最长那行）
2. **报错指向的文件，属于「配置文件」还是「代码文件」？**
   - 配置 → 九成是缩进/逗号/引号问题，用 VS Code 打开对比
   - 代码 → 看 API 名字对不对、版本对不对
3. **最近改过什么？**（版本升级？删字段？换编辑器？）→ **把它改回去验证一遍**，能复现才算真懂。

## 十一、终端命令：bash 与 PowerShell 千万别混用（2026-10-27 记）

**症状**

```powershell
PS C:\Users\<你的用户名>\zero-to-tech> touch index.html
touch : 无法将"touch"项识别为 cmdlet、函数、脚本文件或可运行程序的名称。
```

**原因**：**不是 Windows 不兼容**，是 `touch` / `ls` / `mkdir -p` / `cat` 这些是 **bash（Linux/macOS）** 的命令；PowerShell 是**另一套语言**，不认识它们。

**先判断自己在哪个终端**（看提示符）

| 提示符长相 | 你所在的终端 |
|---|---|
| `PS C:\Users\<你的用户名>>` | **PowerShell** |
| `<你的用户名>@XXX MINGW64 ~` 或 `$` | **Git Bash** |

**解法 A（推荐）：切到 Git Bash**，课程命令原样可用
- 开始菜单搜 **"Git Bash"**，或直接运行：`D:\Git\bin\bash.exe`（本机实际路径）

**解法 B：留在 PowerShell，用等价命令**

| bash（课程用） | PowerShell 等价写法 |
|---|---|
| `touch 文件` | `New-Item 文件`（简写 `ni 文件`；已存在会报错，加 `-Force`） |
| `mkdir 目录` | `New-Item -ItemType Directory 目录`（`mkdir` 别名也能用） |
| `ls` / `pwd` / `cd` | 同名别名可用（`pwd` 能显示路径） |
| `cat 文件` | `Get-Content 文件`（`cat` 别名可用） |
| `rm 文件` | `Remove-Item 文件`（`rm` 别名可用） |
| `rmdir 目录` | `Remove-Item 目录`（空目录）或 `rd 目录` |
| `vim 文件` | 一般没装 → `code 文件`（VS Code）或 `notepad 文件` |
| `clear` | `Clear-Host`（`cls` 也行） |
| `open 文件` | `explorer.exe 文件` 或 `start 文件` |

**结论**：跟这套课程走，**统一用 Git Bash**，能省掉一半踩坑时间。

## 十二、git 的两类"低级报错"（2026-10-28 记）

### 1. 拼写错：`gti init`

```bash
$ gti init
bash: gti: command not found
```

- **原因**：命令名打错（字母顺序反了）
- **判断**：`command not found` = **命令名**不存在/打错，不是没装
- **防呆**：输入 `gi` 后按 **Tab**，bash 自动补全成 `git`

### 2. 少空格：`git add.`

```bash
$ git add.
git: 'add.' is not a git command.
The most similar command is
        add
```

- **原因**：`add.` 被整体当成子命令名；`.` 是**参数**，前面必须有空格
- **正确**：`git add .`
- **连锁反应**：暂存区是空的 → 接着 `git commit -m "..."` 会报
  `nothing added to commit but untracked files present` → **提交根本没发生**

### 3. 如何读 `git status` 的几行关键提示

| 显示 | 含义 | 下一步 |
|---|---|---|
| `No commits yet` | 已 `init`，但**还没有任何提交** | 去 add + commit |
| `Changes to be committed` | 已暂存，**就等 commit** | `git commit -m "说明"` |
| `Changes not staged for commit` | 改过但没 `add` | 先 `git add .` |
| `nothing to commit, working tree clean` | **已提交，工作区干净** ✅ | 可以 push 了 |

### 4. Windows 的换行警告（无害）

```text
warning: in the working copy of '.gitignore', LF will be replaced by CRLF the next time Git touches it
```

- **不用管**：Windows 与 Linux 换行符差异提示，不影响提交和运行
- 想彻底消除：`git config --global core.autocrlf true`
